## T-9 详细记录

检索结果：

| 检索项 | 命中 | 说明 |
|---|---|---|
| `AppConfig.bookshelfLayout` 读取 | **0 处** | 属性已无任何读取方 |
| `AppConfig.bookGroupStyle` 读取 | **0 处** | 同上 |
| 两个属性的 setter 调用 | **0 处** | 无人调用 |
| `PreferKey.bookshelfLayout` | 3 处，均在 `BackupConfig.kt` | 引用的是**常量**，不是 `AppConfig` 属性 |
| `PreferKey.bookGroupStyle` | 1 处，在 `AppConfig.kt` 自身 setter 内 | 若删属性则该引用一并消失 |
| 字符串字面量 `"bookshelfLayout"` / `"bookGroupStyle"` | 仅 `PreferKey.kt` 定义处 | 无散落的硬编码 |

关键事实：**`BackupConfig` 引用的是 `PreferKey.bookshelfLayout`（String 常量），
与 `AppConfig.bookshelfLayout`（Int 属性）是两个不同的东西。**
前者用于备份恢复时的忽略清单，后者已无任何使用者。

评估结论：**建议保持现状，不删**。

理由：

1. 删除 `AppConfig` 两个属性**不影响** `BackupConfig` 的忽略逻辑——它只依赖 `PreferKey` 常量。
   所以「删了会让旧备份恢复失败」这个担心不成立，我此前的 TODO 描述有误。
2. 但保留它们的成本也接近零：只有两个 getter/setter，共 12 行。
3. 真正的风险在于**语义丢失**：这两个 getter 固定返回 0 是「墨水屏专属」这一设计决策的显式表达。
   删掉后，代码里就再也看不到「书架布局被固定」这个事实，未来有人改书架时不会知道这个约定。
4. 若要清理，正确做法不是删属性，而是把它们改成注释更充分的常量说明，或直接删掉并在别处记录该决策。

因此 TODO T-9 的处置改为：**保留属性，修正其 TODO 描述中的错误前提**，并降级为
「记录型事项」而非「待办型事项」。
