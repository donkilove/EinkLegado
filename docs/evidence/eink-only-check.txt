[13c] 分页改为逐项累加填满（自适应条数）
--------------------------------------------------
问题：上一版按「首个子项高度 × 平分可视区」估算条数，是近似算法；且校准只在一次
      post 回调里尝试，列表未渲染完（childCount=0）就直接放弃，回落到初始 8 条，
      TXT 目录规则页因此仍溢出。

修正：
  - 校准改为逐项累加实际高度，累加到超过可视区为止，得到精确容量
  - 校准加入重试（50ms 间隔、最多 20 次），避免渲染未完成时放弃
  - 初始条数设为 8，保证首次渲染量多于一屏，才能测到「填满」的边界

实测（BOOX Poke6，逐项累加后各页面得到不同条数）：
  TXT 目录规则  29 条 → 5 项/页，共 6 页；末项底部 y=1045 < 翻页栏 y=1177
  替换净化      21 条 → 8 项/页，共 3 页；末项底部 y=1111 < 翻页栏 y=1177
  两页均无需滚动，且条数按各自实际项高自动决定（175px 与 113px 的差异被正确体现）

编译：gradlew assembleAppDebug BUILD SUCCESSFUL in 19s。

[18b] 修复章节内位置不随章节同步
--------------------------------------------------
现象：章节能同步，但章节内的页面位置不行。
定位到三个独立原因：

1. ReadBookActivity.onPause 里的同步被 `!BuildConfig.DEBUG` 整块跳过。
   我们装的是 debug 包，该条件恒为 false，因此退出阅读界面从不触发上传——
   日志中完全没有 bookProgress.json 请求。这是最主要的原因。
2. saveRead 在 executor 线程里才给 book 赋值，而 onPause 紧接着并发调用 uploadProgress，
   形成竞态：上传读到的是上一次保存的位置，章节内翻页永远滞后。
3. 上传直接覆盖聚合文件条目，用户回头重读会把云端改成更早的位置，违背「只前进」。

修复：
- onPause 去掉 !BuildConfig.DEBUG 限制
- saveRead 把 book 字段赋值提到调用线程，异步部分只做落库与章节标题更新
- uploadProgress 用内存中的实时章节索引与位置构造进度快照
- AppWebDav 新增 pushProgress：云端已有更靠后进度时不覆盖

实测（《绍宋》，阅读器 6C1DA0B4 → 手机 WWZHIBUKSKCM5LGA）：
  基线：云端 第125章 pos=697
  阅读器打开显示 4/18，翻一页到 5/18，退出
  云端变为 第125章 pos=1620（位置已上传）
  手机冷启动后打开该书显示 8/31 26.0%
  与阅读器 5/18 26.0% 的整本进度一致；页码不同因两屏尺寸不同，属正常分页差异

[20] 数据库体积优化 · 真机验证
--------------------------------------------------
问题：阅读器上数据库实际占用 53.5 MB，其中 legado.db-wal 高达 18 MB（约三分之一）。
      项目只有「压缩数据库」执行 VACUUM，而 SQLite 默认 WAL 模式下仅 VACUUM 不会回收 -wal 文件。
      轮询观察发现：一次操作后 WAL 又涨到 18 MB，说明增长很快，只在启动时处理不够。

优化：
  - 新增 DbMaintenance：checkpoint / shrink / totalSize / configure
  - shrink 改为「先 wal_checkpoint(TRUNCATE) → VACUUM → 再截断」，修复原先只 VACUUM 的问题
  - 启动时设置 wal_autocheckpoint=400（默认 1000 页易被长事务拖住）并执行一次 checkpoint
  - 应用退到后台（Activity 全部 stop）时再 checkpoint

实测（BOOX Poke6）：
  优化前    legado.db 35.45 MB + legado.db-wal 18.06 MB = 53.5 MB
  启动后    legado.db 35.40 MB + legado.db-wal  2.90 MB = 38.3 MB   ← 回收 15.2 MB
  退后台    保持 2.90 MB（后台 checkpoint 生效，未再膨胀）
  手动压缩  主库 35.37 → 34.66 MB（VACUUM 减 0.7 MB），
           但 VACUUM 期间 WAL 会暂时暴涨到 34.9 MB（重建表产生大量写入），
           需靠下次启动或退后台的 checkpoint 回收，实测重启后降到 6.8 MB、再启动降到 2.9 MB

结论：体积问题的主因是 WAL 长期未回收，非数据本身冗余。主库 35 MB 为章节缓存与书籍数据，压缩空间有限。

[21] 编译缓慢排查：in-process 策略禁用增量编译
--------------------------------------------------
现象：改一个 Kotlin 文件后 assembleAppDebug 需 5~6 分钟，长期无法忍受。
profile 显示 compileAppDebugKotlin 占 4m47s（总 5m41s），其余任务均在 20s 内。

排查掉的非根因：
  磁盘       NVMe SSD，非 I/O 瓶颈
  JDK        17，版本足够
  Kotlin     2.3.10，K2 已启用，无升级空间
  注解处理    已是 KSP，不存在 kapt 开销
  内存       6G + 编译器 4G，充足
  杀毒       Defender 已排除项目与缓存目录，无改善（316s → 372s，含配置缓存重建）
  caching/parallel  早已开启
  配置缓存    项目构建脚本用 'git rev-list'.execute() 在配置阶段起外部进程导致无法保存，
             改用 providers.exec 后修复，但仅省约 20~25s

根因（Kotlin 构建报告）：
  开启 kotlin.build.report.output=file 后，报告明确写出：
    REBUILD_REASON: In-process execution
    Non incremental inprocess compilation: 147.777 s
  即此前为提高速度加的 kotlin.compiler.execution.strategy=in-process
  会使 Kotlin 强制全量编译——增量编译在该策略下不生效。

修复：移除 in-process，恢复默认 daemon 策略。

修复后实测（改一个 Kotlin 文件后 assembleAppDebug）：
  第 1 轮  20.3 s
  第 2 轮  31.2 s
  无变更   10.9 s
  Kotlin 任务 9.7 s，其中 Incremental compilation in daemon 5.9 s
  配置阶段 0.537 s（配置缓存命中）

结论：从 316~372s 降至 20~31s，约 10~15 倍提升。
教训：优化编译速度的手段本身可能反而破坏增量，必须用 kotlin.build.report 验证。
